# OpenAPI Client (Quarkus) – Consolidated Technical README

## 1. Overview
This project is a Quarkus-based client application that consumes an external Pet Store API using code generated from an OpenAPI specification (`src/main/openapi/pet_store.yaml`). It demonstrates:
- Quarkus OpenAPI Generator usage (generated `DefaultApi` client)
- Layered architecture (Resource → Service → Generated Client)
- Graceful degradation with mock data fallback
- Header capture + propagation (client-side filters)
- Logging, configuration, and testing best practices

## 2. Architecture Summary
```
Request
  ↳ JAX-RS Resource (`MyResource`, `HeaderTestResource`)
      ↳ Service Layer (`PetService`)
          ↳ Generated REST Client (`DefaultApi`) from pet_store.yaml
              ↳ Filters:
                  - Server: HeaderCaptureFilter (captures incoming headers into Vert.x context)
                  - Client: PetStoreHeaderPropagationFilter (propagates headers)
                  - Client: PetStoreClientLoggingFilter (logs outbound requests)
Fallback: PetService mock data when external API unavailable
```
Supporting packages:
- `service` – business logic, fallback handling
- `client` – request filters (propagation + logging)
- `server` – container request filter for header capture
- `petstore.*` – generated by OpenAPI generator

## 3. Generated Client
The OpenAPI Generator (Quarkus extension) produces a `DefaultApi` REST client at build time.
Key settings (from `application.properties`):
```
quarkus.openapi-generator.codegen.spec.pet_store_yaml.base-package=org.acme.openapiclient.petstore
quarkus.openapi-generator.codegen.spec.pet_store_yaml.config-key=pet_store_yaml
quarkus.openapi-generator.codegen.spec.pet_store_yaml.return-response=true
quarkus.openapi-generator.codegen.spec.pet_store_yaml.enable-security-generation=false
```
REST client configuration (using the config-key):
```
quarkus.rest-client.pet_store_yaml.url=${petstore.api.url}
quarkus.rest-client.pet_store_yaml.scope=jakarta.inject.Singleton
quarkus.rest-client.pet_store_yaml.connect-timeout=5000
quarkus.rest-client.pet_store_yaml.read-timeout=30000
# (Providers registration line can be uncommented if desired)
# quarkus.rest-client.pet_store_yaml.providers=org.acme.openapiclient.client.PetStoreHeaderPropagationFilter,org.acme.openapiclient.client.PetStoreClientLoggingFilter
```
Injection pattern (recommended):
```java
@Inject
@RestClient
DefaultApi petStoreApi;
```

## 4. Header Propagation Design
Goal: propagate all relevant incoming request headers to outbound REST client calls without hardcoding.
Current approach:
1. `HeaderCaptureFilter` (ContainerRequestFilter) iterates incoming headers, stores selected ones in Vert.x context (excluding hop-by-hop/connection-specific headers).
2. `PetStoreHeaderPropagationFilter` retrieves known headers from Vert.x context and adds them to `ClientRequestContext`.
3. `PetStoreClientLoggingFilter` logs method, URI, and headers; warns if critical headers (Authorization, X-Request-ID) missing.

Future enhancement (documented, not yet implemented): store a Map<String,String> of all non-excluded headers in Vert.x context and iterate keys in the client filter to avoid maintaining a static list.

Excluded headers (not propagated): Host, Connection, Content-Length, Transfer-Encoding, Upgrade, Accept-Encoding, TE, Trailer, Proxy-Authorization, Proxy-Authenticate, Keep-Alive.

## 5. Mock Data Fallback
`PetService` first attempts remote calls (e.g., `petsGet`, `petsPetIdGet`, `petsPost`). If the external API is unavailable or returns non-200 status, it falls back to deterministic mock data (Fluffy, Buddy, Tweety) or simulates creation.
Benefits:
- No 500 errors for basic fetch scenarios
- Allows development/testing without external dependency

## 6. Known Issues & Resolutions
| Issue | Symptom | Root Cause | Resolution |
|-------|---------|------------|-----------|
| ClassCastException when reading entities | `InputStreamWrapper cannot be cast` | Using `Response` with `return-response=true` and raw `List.class` casts | Prefer `return-response=false` to get typed returns OR use `response.readEntity(new GenericType<List<Pet>>() {})` and try-with-resources |
| Missing bean injection warning | Rest client field un-injected | Lacked `@Inject` annotation | Add `@Inject @RestClient` to `DefaultApi` field |
| CredentialsProvider build error (earlier) | BuildException referencing ConfigCredentialsProvider | Security generation expected credentials bean | Keep `enable-security-generation=false` or implement CredentialsProvider bean |
| Headers not appearing in outbound requests | Logging shows missing Authorization/X-Request-ID | Capture filter didn’t store / propagation list incomplete | Ensure server capture filter runs, providers registered, persist dynamic header map (future) |
| Duplicate provider registration warning | `Provider instance ... already registered` | Provider added twice (auto + manual) | Remove duplicate registration (keep one configuration path) |

## 8. Quick Start
### Build & Dev
```bash
./mvnw clean compile
./mvnw quarkus:dev
```
Visit:
- App: http://localhost:8779
- Dev UI: http://localhost:8779/q/dev/
- OpenAPI: http://localhost:8779/openapi
- (If Swagger UI enabled) http://localhost:8779/swagger-ui

### Basic cURL
```bash
# Health
curl http://localhost:8779/api/pets/health

# Get pets (fallback mock if external API absent)
curl http://localhost:8779/api/pets?limit=2

# Get pet by ID
curl http://localhost:8779/api/pets/1

# Create pet
curl -X POST http://localhost:8779/api/pets \
  -H "Content-Type: application/json" \
  -d '{"name":"Max","tag":"dog"}'
```

### Header Propagation Test
```bash
curl -v \
  -H "Authorization: Bearer test-token-123" \
  -H "X-Request-ID: req-456" \
  -H "x-custom-header: look-at-me" \
  http://localhost:8779/api/test/headers
```
Check logs for propagated headers in outbound request.

## 9. Testing
Run all tests:
```bash
./mvnw test
```
Test categories:
- Integration (resource-level validation, error handling)
- Mocked service tests (using `@InjectMock`) for deterministic scenarios

If external API is absent, integration tests expecting remote success will show fallback or 500 depending on path — this is intentional.

## 10. Troubleshooting
| Symptom | Possible Cause | Action |
|---------|----------------|--------|
| Missing generated classes (`petstore.*`) | Generator not run yet | `./mvnw clean compile` |
| `DefaultApi` null | Missing `@Inject` | Add `@Inject @RestClient` |
| Headers not propagated | Providers not registered | Uncomment providers property or ensure filters annotated/registered |
| ClassCastException on response entity | Raw `List.class` read with `return-response=true` | Change generator setting or use `GenericType<List<Pet>>` |
| Build failure referencing credentials provider | Stale generated security code | Clean build + keep security generation disabled |

## 11. Future Enhancements (Backlog)
- Dynamic full-header propagation via stored Map in Vert.x context

## 12. Security Considerations (Spec Needs Hardening)
Current `pet_store.yaml` is minimal — production hardening should add:
- Security schemes (JWT/OAuth2)
- Input validation (patterns, min/max, enums)
- Error response schemas
- Rate limiting headers
- Versioned paths (`/v1/pets`)

## 13. Key Lessons
- Use config-key to cleanly bind generated client to REST properties.
- Avoid nested try-catch: extract API-call logic and fallback paths.
- Logging filters clarify runtime header state and propagation gaps.
- Mock fallback enables local development independent of external systems.

## 14. Minimal Code Snippets
Header capture (simplified):
```java
@Provider
public class HeaderCaptureFilter implements ContainerRequestFilter {
  public void filter(ContainerRequestContext ctx) {
    var vx = io.vertx.core.Vertx.currentContext();
    if (vx == null) return;
    ctx.getHeaders().forEach((k,v)-> { /* store non-hop-by-hop */ });
  }
}
```
Rest client injection:
```java
@ApplicationScoped
public class PetService {
  @Inject @RestClient DefaultApi petStoreApi; // generated client
}
```
Mock fallback fragment:
```java
if (remotePets == null) return mockPets(limit);
```

## 15. Maintenance Guidelines
- Regenerate client after OpenAPI spec changes: `./mvnw clean compile`
- Keep provider registration singular to avoid duplicate warnings.
- Prefer constructor or field injection with qualifiers.
- Centralize header names if moving to dynamic propagation.
